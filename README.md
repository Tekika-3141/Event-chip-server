# 文化祭チップ管理システム

文化祭イベントで、参加者ごとに割り当てた任意のコード（QRコード／USBスキャナー／手入力）を使い、
保有チップを複数端末から管理するための、軽量なWebシステムです。
**イベント内のチップのみを扱います（現金・電子マネーは扱いません）。**

## 機能

- 参加者コードの登録（任意の文字列。重複不可）、有効／無効の切り替え
- セッション管理（開始・終了。同じコードを次の参加者に再利用でき、過去のセッションは残る）
- チップの加算・減算（サーバー側SQLiteトランザクションで処理し、履歴を同時に記録）
- ゲーム名の記録、ゲーム名の追加・名前変更・停止、ゲーム別集計
- 管理者による手動修正（履歴を書き換えず「管理者修正」の行を追加）
- **チップ設定**: 新規登録するプレイヤーの初期チップ数を管理画面で設定（再起動後も保持）
- **プレイヤーの初期状態リセット**: 特定のコードの現在セッションを終了し、次回を初期チップから開始できる状態に戻す（履歴は残る）
- **データベース初期化**: 参加者コード・セッション・チップ履歴を自動バックアップ後に一括削除（ゲーム設定・チップ設定・管理者パスワードは残る）
- 履歴確認（コード／セッション単位）
- DBバックアップ（管理画面またはコマンド）
- 簡易サーバーログ（管理画面で表示、`data/server.log` にも保存）
- QRコードの**読み取り**（スマホカメラ。ただし下記の制約あり）

## 動作環境

- サーバーPC: Python 3.8 以上（開発・自動テストは Python 3.12 で実施）
- クライアント: ブラウザのみ（Node.js・Python 不要）

## 必要なソフトウェア

- Python 3（標準ライブラリのみ。`pip install` は不要）
- 同梱ファイル: `static/jsQR.js`（QR読み取りライブラリ jsQR 1.4.0、Apache-2.0。ライセンスは `static/jsQR.LICENSE.txt`）

## インストール方法

フォルダごとサーバーPCにコピーするだけです。ビルドや `npm` / `pip` は不要です。

## 起動方法

```
python server.py
```

- 初回起動時に管理者パスワードを自動生成し、画面に表示して `data/admin_password.txt` に保存します。
  環境変数 `ADMIN_PASSWORD` を設定した場合はそちらが優先されます。
- ポート変更: `python server.py --port 8080`
- 止めるには `Ctrl+C`。データは `data/system.db` に保存され、再起動しても残ります。

## LAN内からのアクセス方法

起動時に表示される「LAN内の端末」のURL（例: `http://192.168.1.100:8000/`）を、他の端末のブラウザで開きます。
IPアドレスは環境によって異なります。つながらない場合はサーバーPCのファイアウォール（ポート8000の受信許可）を確認してください。

| 画面 | URL |
|---|---|
| トップ | `/` |
| ディーラー画面 | `/dealer` |
| 管理画面 | `/admin` |

## 管理画面

`/admin` を開き、管理者パスワードでログインします。管理者用APIはサーバー側でログインCookieを確認しており、
ディーラー画面からは管理操作（コード登録・セッション開始/終了・チップ修正・バックアップ等）はできません。

- 参加者コード一覧（コード／状態／現在チップ／セッション開始／最終更新）、自動更新（5秒ごとのポーリング、任意）
- 新規コード登録、セッション開始・終了、**初期状態に戻す**、コードの有効／無効
- **チップ設定**（初期チップ数）
- チップ手動修正（確認ダイアログあり）
- 履歴確認、ゲーム名の管理、ゲーム別集計
- バックアップ作成・一覧、サーバーログ表示
- **システム管理: データベース初期化**（赤枠の別カード。通常の操作ボタンとは見た目で区別しています）

### チップ設定（初期チップ数）

- 管理画面の「チップ設定」カードに現在の初期チップ数が表示されます。0以上の整数を入力して「保存」します
  （上限は保有チップの上限と同じ 100,000,000）。
- 保存した値は SQLite の `system_settings` テーブル（`default_initial_chips`）に入り、サーバーを再起動しても残ります。
- 「新規コード登録」の初期チップ欄には、この設定値が自動で入ります（登録のたびに手で変更することもできます）。
  API で `initial_points` を省略して登録した場合も、この設定値が使われます。
- **既存のプレイヤーの `initial_points`、進行中のセッションの現在チップ、過去のセッション・履歴は一切変更されません。**
  設定を変えた後に新しく登録するプレイヤーにだけ適用されます。

### プレイヤーを初期状態に戻す

- 参加者一覧の各行の「初期状態に戻す」ボタン。押すと確認ダイアログが出て、「OK」の場合のみ実行されます。
- 実行すると、そのコードの**進行中のセッションを終了**します（終了したセッションと全履歴はそのまま残ります）。
  参加者コード自体は削除されません。次に「セッション開始」すると、そのプレイヤーの初期チップから始まります。
- 進行中のセッションが無い場合（未開始・終了済み）でもエラーにならず、「次回は初期チップから開始」の状態として扱います。
- 履歴を消す・書き換えるリセットではありません。実行内容はサーバーログに記録されます（`ADMIN reset code ...`）。
- 存在しないコードを指定するとエラー（404）になります。

### データベース初期化

イベント終了後・テスト終了後に、運用データをまとめて消して新しく始めるための機能です。

| | 内容 |
|---|---|
| 削除する | 参加者コード、セッション、チップ履歴（それに紐づく運用データ） |
| 削除しない | ゲーム設定（停止中の状態も含めそのまま）、チップ設定（初期チップ数）、管理者パスワード（`data/admin_password.txt`）、DBファイル自体 |

手順（管理画面）: 「システム管理」カードで確認欄に `INITIALIZE` と入力（一致するまでボタンは押せません）→
ボタンを押す → 強い確認ダイアログで「OK」→ 自動バックアップ → 初期化。

- **サーバー側でも確認文字列を必須**にしています（API を直接呼んでも、`confirm: "INITIALIZE"` が無いと実行されません）。
- **初期化の前に必ず `backups/system-YYYYMMDD-HHMMSS.db` を作成**し、そのファイルが開けて壊れていない
  （`integrity_check`）ことを確認します。**バックアップに失敗した場合は初期化しません**（データは何も消えません）。
- 削除は 1 つのトランザクション（`BEGIN IMMEDIATE`）で行います。途中でエラーが出たら全部ロールバックされ、
  一部だけ消えた状態にはなりません。エラーメッセージは管理画面に表示されます。
- 履歴テーブルは追記専用トリガー（UPDATE／DELETE禁止）で守られています。初期化では、同じトランザクションの中で
  DELETE禁止トリガーだけを一時的に外して履歴を消し、**トリガーを作り直してから COMMIT**します。途中で失敗した場合は
  トリガーも含めて元に戻ります。通常の操作（チップ変更など）では履歴は引き続き追記専用です。
- 初期化後は、参加者コード・セッション・チップ履歴が 0 件になり、ID（セッション番号など）も 1 から振り直されます。
  管理者はログインしたまま、同じパスワードで新しいコードを登録して運用を始められます。
- 初期化の前後はサーバーログに記録されます（`ADMIN database initialized ...`）。

**バックアップからの復元（画面の機能はありません。手動）**: サーバーを止める → `backups/` の対象ファイルを
`data/system.db` に上書きコピー → `data/system.db-wal` と `data/system.db-shm` があれば削除 → サーバーを起動。

### 管理者API（すべて管理者ログイン必須。未ログインは 401）

| メソッド・パス | 内容 |
|---|---|
| `GET /api/admin/settings` | 現在の初期チップ数を取得 |
| `POST /api/admin/settings` | `{"default_initial_chips": 500}` で初期チップ数を変更 |
| `POST /api/admin/participants/reset` | `{"code": "..."}` でプレイヤーを初期状態に戻す |
| `POST /api/admin/system/initialize` | `{"confirm": "INITIALIZE"}` でバックアップ後にDB初期化 |

ディーラー画面（ログイン不要）から呼べるのは `/api/participant`、`/api/games`、`/api/points/change` だけです。

## ディーラー画面

1. 操作者名を入力（端末に記憶されます）
2. QRスキャナー／手入力／カメラで参加者コードを入力 → 現在チップを大きく表示
3. ゲームを選び、`+100` などのボタンか直接入力でチップ変更量を指定 → 「チップ変更」

サーバーに接続できない場合は「サーバーに接続できません。操作は実行されていません。」と表示し、
クライアント側で勝手に保存・後から同期することはしません。
チップがマイナスになる減算は拒否されます。

## QRコードについて

**QRコードは外部サービス等で作成し、本システムではQRコードの読み取りのみを行います。**
QRコードの生成・編集・印刷の機能はありません。QRの内容（例: `2026_A_001`）がそのまま参加者コードになり、
データベースに保存されるのは参加者コードの文字列だけです（QR画像は保存しません）。

## QR読み取りについて

3つの入力方法はすべて同じ「コード検索」処理（`static/dealer.js` の `lookupCode`）に合流します。

1. **USB QRスキャナー**: キーボード入力型のスキャナーを想定。コード入力欄にフォーカスがある状態で読み取ると、
   コードと Enter が入力されて検索されます（入力欄は検索後に自動で空になり、フォーカスが戻ります）。
2. **手入力**: コード入力欄に入力して Enter か「検索」。
3. **スマホ／PCのカメラ**: 「QRを読み取る（カメラ）」ボタン。同梱の jsQR で映像をデコードします。

### カメラ利用の制約（重要）

ブラウザの仕様上、カメラ（`getUserMedia`）は **HTTPS または localhost** のページでしか使えないのが一般的です。
`http://192.168.x.x:8000/` のような単純なHTTPのLANサイトでは、スマホのブラウザでカメラが使えない可能性が高いです
（使えない場合、画面に理由を表示します。手入力とUSBスキャナーはHTTPでも動作します）。

HTTPSで起動する手順（サーバー側のHTTPS起動は動作確認済み。**スマホ実機でのカメラ動作は未確認**）:

1. サーバーPCで自己署名証明書を作る（`openssl` が必要。Git for Windows に同梱されています）:
   ```
   openssl req -x509 -newkey rsa:2048 -nodes -keyout data/key.pem -out data/cert.pem -days 30 -subj "/CN=localhost"
   ```
2. `python server.py --https` で起動し、`https://<サーバーのIP>:8000/` を開く。
3. 自己署名証明書なので、ブラウザに警告が出ます。警告を承諾して進む必要があります。
   承諾後にスマホでカメラが使えるかどうかは、機種・ブラウザによって異なる可能性があり、本プロジェクトでは未確認です。

運用案: チップ操作は通常のHTTPで行い、カメラを使う端末だけHTTPSのURLにする（同じサーバーを2ポートで起動する機能は
ありません。HTTPとHTTPSを併用するには `--port` を変えて2つ起動する必要があり、同じ `data/` を共有するため
SQLiteのロックで整合性は保たれますが、この構成は実機未確認です）。

## データベース

- SQLite（`data/system.db`）。テーブル: `participants`（参加者コード）、`sessions`（セッション）、
  `point_history`（チップ履歴）、`games`（ゲーム名）、`system_settings`（システム設定。初期チップ数など）
- 画面・メッセージ・READMEでは「チップ」に統一しましたが、既存DB・APIとの互換性のため、内部の名前
  （`point_history`、`initial_points`、`current_points`、`/api/points/change`、JSONの `points` など）は変更していません。
- **既存のDBはそのまま使えます。** 起動時に `system_settings` テーブルが無ければ自動で追加され（`CREATE TABLE IF NOT EXISTS`）、
  既存の参加者・セッション・履歴・ゲームは変更されません。初期チップ数の初期値は 100 です（従来の画面の初期値と同じ）。
- チップ変更は `BEGIN IMMEDIATE` のトランザクション内で「現在値の取得 → 更新 → 履歴追加 → COMMIT」を行い、
  失敗時は両方ロールバックします。クライアントから送られるのはチップ変更量だけで、現在チップは受け付けません。
- 同じ `request_id` の操作を再送しても二重には適用されません（通信エラー後の再試行用）。
- 履歴はトリガーで UPDATE／DELETE を禁止しています（追記専用）。訂正は管理者修正の新しい行で行います。
- ゲーム名を変更しても過去の履歴の名前は変わりません（集計は当時の名前ごとに分かれます）。
- 1つのコードにつき、進行中のセッションは同時に1つだけです。
- 時刻はサーバーPCの時計（ローカル時刻）です。

## バックアップ

- 管理画面の「今すぐバックアップを作成」、またはコマンド `python server.py --backup`
- `backups/system-YYYYMMDD-HHMMSS.db` に保存（SQLiteのバックアップAPIを使用。元のDBは変更されません）
- `data/admin_password.txt` はバックアップに含まれません。
- データベース初期化の直前にも、同じ方法で自動的にバックアップが作られます（上記「データベース初期化」）。

## 既知の問題

- 管理者パスワードは `data/admin_password.txt` に平文で保存されます（LAN内利用前提）。通信がHTTPの場合、パスワードも平文で流れます。
- 管理者ログインの総当たり対策は、失敗時に0.5秒待つだけです。
- ログインセッション（Cookie）はサーバー再起動で無効になります。
- ディーラー画面には認証がありません（LAN内の誰でも開けます）。操作者名は自己申告で、端末のIPアドレスも履歴に記録されます。
- `server.log` は自動でローテーションされません。表記変更前に書かれた古いログ行（`POINT`・`pt`）は書き換えていません。
  新しい行から `CHIP`・`チップ` になります。
- データベース初期化では、バックアップ作成から削除までの間（ごく短時間）に他の端末が行ったチップ変更は、バックアップには入りません。
  イベント終了後など、ディーラー側の操作が止まってから実行してください。
- バックアップからの復元は手動です（画面の復元機能はありません）。
- QRのデコードは jsQR のみ使用（ブラウザ標準の BarcodeDetector は使っていません）。映像条件によっては読み取りにくい場合があるかもしれませんが、実機では未確認です。
